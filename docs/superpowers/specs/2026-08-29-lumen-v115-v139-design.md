## Shared context

### The condition that produced these builds

At some point after v106, `app.js` was switched from a classic `<script>` to `<script type="module">`. That single change is the origin of B1 in full and parts of B5: ES modules have their own top-level scope, so `app.js`'s 342 top-level functions stopped being global. Nothing announced this. The failures it caused were silent — dead click handlers, stale object references, tests reaching for identifiers that no longer existed.

The v104–v106 spec explicitly forbade this: *"`app.js` stays a classic `<script>` (not `type=module`) — it relies on hundreds of inline `onclick="fn()"` handlers that need functions in global scope."* The cutover happened anyway, without the handler migration that would have made it safe.

### Constraints carried across all twenty-two builds

- **Behavior preserved unless a defect is being fixed.** Every build ran the full suite before and after.
- **Every fix pinned by a test watched failing first.** Where a test passed for the wrong reason, it was rewritten or removed rather than kept.
- **`dist/` is the artifact** (established in B2). The source tree is a dev convenience.
- **Release ritual.** Each build bumps `sw.js` `VERSION`; `SHELL` is regenerated from the built output; `index.html` no longer carries `?v=` query params (Vite content-hashes instead).
- **Local-first.** No new runtime dependency, no new network call, no telemetry.

## B1 — v115: Restore the handler contract

### Goal

Make `app.js`'s ES-module scope safe for the code and tests that assumed global scope.

### The defect

Verified in a real browser before any edit:

```
window.closeModal    → "undefined"
window.renderFinance → "undefined"
```

Clicking a modal's ✕ raised `ReferenceError: closeModal is not defined` and **left the modal open**. 46 inline `onclick="closeModal()"` sites were affected — every modal's close and cancel control. Only the backdrop-click path still dismissed a modal.

### Design

Inline handlers can only see globals, so the handlers stop being inline. 46 sites became a declarative `data-close-modal` attribute, read by one delegated listener on `document` (`app.js:1614`) that survives every `innerHTML` re-render and covers controls inside and outside `#modal-root`. The attribute's value names optional follow-up work (`finance`, `finance-if-active`), replacing the two sites that chained calls inline.

For the test suite, a deliberate seam rather than incidental globals: `window.__LUMEN_TEST` (`app.js:13803`) names 12 functions on purpose, with **getters** for the mutable `syncMeta` and `undoStack` bindings so specs observe reassignment. 28 call sites across four specs were repointed; no assertion was changed.

### Two further defects found

Both were production bugs, not test artifacts, and both were wrongly folded into B1's original cause estimate — only 12 of the 20 failing specs came from the handler contract.

**Reload showed an empty app in the wrong theme.** `load()` deferred *all* hydration to `requestIdleCallback`, but `init()` runs `applyTheme()` and `renderView()` immediately after it — both against default state, with nothing re-rendering afterward unless IndexedDB happened to disagree with localStorage. Fixed at `app.js:718` by making the localStorage read synchronous (one `getItem` plus a `JSON.parse`; the static shell already paints from `index.html` before `app.js` runs) and deferring only the genuinely async IndexedDB upgrade.

> A first attempt — a catch-up re-render *after* hydration — passed the hydration tests but broke three others by stealing focus from anyone typing during boot. That was a real production hazard, not just a test failure, which is why the fix restructures rather than patches.

**`window.state` went stale.** `performUndo`, `performRedo`, backup import and "reset all data" all do `state = ...`, rebinding the module variable, while `window.state = state` held the pre-rebind object. `src/state/store.js`'s `getState()` therefore handed stale data to every consumer. Replaced with a live accessor at `app.js:13787`.

### Files

| File | Change |
| :-- | :-- |
| `app.js` | 46 inline handlers → `data-close-modal`; delegated listener; `__LUMEN_TEST` seam; synchronous LS hydration; live `window.state` accessor |
| `tests/module-scope.spec.js` | **new** — 4 tests: source-level fence, modal close, live state binding |
| `tests/hydration.spec.js` | **new** — 2 tests: state and theme survive reload without navigating |
| `tests/regression.spec.js` | stale `LumenLib` namespace inventory (7 of the actual 10) corrected |

## B2 — v116: Make the production artifact real

### Goal

Ship one artifact, and make it a working PWA.

### The defect

`dist/` contained **no `sw.js` at all**, and all three manifest icons 404'd. `vercel.json` declared no `framework` or `outputDirectory`, so which of two artifacts shipped was left to zero-config detection.

The subtlest part: `start_url`, `scope` and `icons[].src` in a web manifest resolve against **the manifest's own URL**, not the page's. Vite content-hashes the manifest into `assets/`, so `"start_url": "./"` silently scoped the installed app to `/assets/`.

Nothing caught any of it. `offline.spec.js` tested the *source tree*, and the service worker's `Promise.allSettled` swallows every precache failure.

### Design

`scripts/postbuild.js` replaces `generate-sw.js`. It copies the four icons Vite never sees into `dist/`, derives `SHELL` by walking the finished `dist/`, then ships `sw.js`. The old generator **unioned** the source tree with the built assets, which is why roughly half of every `SHELL` 404'd whichever way the app was served.

Manifest `start_url`, `scope` and icon paths became root-absolute, so they resolve wherever the build puts the manifest.

`npm run build` now runs the postbuild step. Previously `generate-sw.js` was manual, so any build without it left `SHELL` pointing at stale content hashes.

### The judgment call

**One artifact.** `tests/offline.spec.js` was retargeted from the repo root to `dist/`. A service worker whose precache list is generated from `dist/` cannot also be validated against the source tree.

The cost, stated plainly: `npm start` serves the repo root, where the SW now precaches `dist/` paths that 404 there. The dev app still works via runtime caching and network fallback, but no longer boots offline. That was incidental capability, not a requirement, and no test asserted it.

### Files

| File | Change |
| :-- | :-- |
| `scripts/postbuild.js` | **new**, replaces `scripts/generate-sw.js` |
| `package.json` | `build` → `vite build && node scripts/postbuild.js` |
| `manifest.webmanifest` | `start_url`, `scope`, icon paths → root-absolute |
| `vercel.json` | `buildCommand` + `outputDirectory` pinned; immutable `/assets/*`; webmanifest MIME rule retargeted to where the manifest lands |
| `sw.js` | `SHELL` marked generated; header comment corrected (it described a `?v=` scheme `index.html` had dropped) |
| `tests/dist-artifact.spec.js` | **new** — 3 tests: SW present, every `SHELL` entry resolves, manifest + icons + `start_url` resolve |
| `tests/offline.spec.js` | retargeted to `dist/` |
| `README.md` | the "requires zero build steps" deployment claim, made false by this build |

### Outcome

`SHELL` entries resolving: 6 of 34 → **13 of 13**. Playwright 81 → **84**.

## B3 — v117: Modal and palette accessibility

### Goal

Make Lumen's dialogs usable by keyboard and screen reader.

### The finding that shaped it

The pitch said "93 modal constructions, zero `role="dialog"`". The 93 turned out to be **one**: every modal routes through `openModal(html)` (`app.js:1554`), the only place in the app that writes `#modal-root`. So dialog semantics could be *applied to* the caller's markup rather than *edited into* 93 HTML strings. **Zero call sites changed.**

### Design

`openModal` now applies, to whatever markup it was handed:

- `role="dialog"`, `aria-modal="true"`, `tabindex="-1"`
- `aria-labelledby` wired to the modal's own `<h3>`, id generated if absent — the name is always the visible heading, never a hardcoded string
- a **focus trap** on Tab/Shift+Tab wrapping at both ends, using `getClientRects()` rather than `offsetParent` (the backdrop is `position: fixed`, which makes `offsetParent` null for everything inside it)
- **focus restored** to whatever opened the modal, captured only on the outermost open so a modal replacing another doesn't capture a node about to be destroyed
- accessible names for icon-only buttons, falling back to `title` then to `"Close"`

`closeModal` (`app.js:1598`) also fixes a **listener leak**: the old Escape handler only unbound itself when *Escape* closed the modal, so every other dismissal path leaked one `keydown` listener per modal opened.

The Ctrl+K command palette (`app.js:13133`, `app.js:13440`) got the same contract. It doesn't route through `openModal`, so it had none of it — and it is the most keyboard-driven surface in the app.

### Correction to the original pitch

B3 was pitched partly on *"6 places set `outline: none`, so the focus trap moves focus invisibly."* **That was wrong.** `styles.css:313` replaces the outline with `box-shadow: 0 0 0 3px rgba(96,93,255,.18)` — the inputs do show focus. A `:focus-visible` rule and its test were written on that premise; the test passed identically with and without the CSS, which is how the error surfaced. Both were reverted rather than shipping an unproven change with a test that proves nothing.

Left open, unverified: that ring is 18%-alpha accent on `--surface2`, which may fall short of the 3:1 WCAG 2.2 requires, across eleven themes. That needs measurement, not a guess.

### Files

| File | Change |
| :-- | :-- |
| `app.js` | `openModal`/`closeModal` rewritten; palette given the same contract |
| `tests/a11y-modal.spec.js` | **new** — 7 tests, including a breadth test across four modal types, verified to fail by temporarily removing the `role` assignment |

### Outcome

Playwright 84 → **91**.

## B4 — v118: Repair the unit-test seam

### Goal

One unit-test runner, unmasked in CI.

### The defect

`npx vitest run` found **0 tests in all 10 files** — they were written against `node:test`. CI hid it with `npm run test:vitest --if-present || echo "vitest skipped"`, so `npm run test:all` had been broken without anyone seeing a red build.

### The decision

Two runners, both defensible; the v104 plan specified Vitest while the code used `node:test`. Resolved in favour of **Vitest**, because it is already the project's build tool's test runner, is already configured in `vite.config.mjs`, and gives jsdom — which the god-file split will want when view modules that touch the DOM get extracted.

The migration was 10 import lines: `node:assert/strict` runs unchanged under Vitest, so all 103 assertions stayed byte-identical. The one real port was `node:test`'s `mock.fn` → `vi.fn` in `tests/unit/gemini.test.js`, where the call-count API differs.

### A bug the migration surfaced

Playwright's default `testMatch` includes `*.test.js`, so **it had been loading `tests/unit/**` all along**. Under `node:test` those imports were inert; under Vitest `describe` throws outside its runner, which is how it appeared. Both Playwright configs now set `testMatch: '**/*.spec.js'` — E2E is `.spec.js`, unit is `.test.js`, no overlap.

### Dead weight removed

125 lines across three modules, all with **zero reachable call sites**:

| Removed | Why |
| :-- | :-- |
| `src/perf/memo.js` | nothing imported it; the memo logic it duplicated lives inline in `app.js` |
| `src/state/store.js` | `getState`/`bumpStateRev` called nowhere |
| `src/state/undo.js` | all six exports unused; `app.js` has its own `pushUndoSnapshot`. **Two implementations of undo, one unreachable** — the strongest case of the three |
| `LumenLib.constants` | zero consumers. `src/lib/constants.js` itself stays: `crypto.js`, `vault-worker.js` and a unit test import it directly |
| `src/views/`, `src/workers/`, `src/sync/` | empty placeholder directories |

### Outcome

Vitest 0 → **67 tests**. `npm run test:all` works. CI unmasked.

## B5 — v119: Vault store extraction (first slice)

### Goal

Begin splitting the god-file, starting with the vault — the seam that already existed and had eight passing specs as a net.

### The defect it uncovered

The "seam" was not dead code. It was a **cycle**. `app.js`'s `vaultGuessType` delegated to `LumenLib.vault.vaultGuessType`, and `app.js` assigned that same delegator *back onto* `LumenLib.vault`. The function called itself.

Verified in a real browser before any edit: `vaultGuessType('notes.pdf', 'application/pdf')` → `RangeError: Maximum call stack size exceeded`.

User-visible damage: `syncType()` calls it the moment a file is picked in the vault modal. It threw mid-handler, so **type auto-detect and title auto-fill silently never ran** — pick a CSV, the type stayed "link". The existing upload test passed straight through it because it fills the title by hand and never checks the type select.

> A half-finished extraction is more dangerous than no extraction: the delegator looks like the refactor already happened.

### Design

**Move A — vault store layer → `src/vault/store.js`.** `vaultDb`, `vaultBlobPut/Get/Delete`, `vaultQuotaUsed`, `vaultGuessType`, `vaultTypeIcon`, and the `VAULT_*` constants. `app.js` keeps one-line delegators through `VaultStore` (`app.js:901`), plus the two genuinely app-level concerns wrapped around them: the quota memo (keyed on `_stateRev`) and the toast debounce. `VAULT_TYPES` and `vaultTypeLabel` moved to `src/vault/view.js`.

The `Object.assign` boundary (`app.js:7691`) is now honest — only the five app-owned functions (`getVaultItems`, `getVaultCollections`, `getVaultFiltered`, `openVaultModal`, `renderVault`, which read `state`/`vaultFilter`/the DOM) are published back. The store-layer names stay the module's.

**Move B — `fileSizeStr` → `src/lib/helpers.js`.** Pure 5-line formatter, 9 call sites, now with 3 unit tests it never had. Done as its own verified move because it is a prerequisite for the next slice.

### Where the split stops, and why

The HTML fragment builders (`vaultCardHTML`, `vaultRowHTML`, `vaultWidgetHTML`) were **not** moved. They depend on `tagSpan` and `fmtShort`, which pull in tag colours from `state` and date formatting from settings — a cascading dependency graph, not one boundary. Moving them now would mean either dragging three more subsystems along or changing signatures to inject dependencies, which breaks the public interface the refactor exists to preserve.

**Honest measure:** `app.js` is 13,804 lines — this did not meaningfully shrink it. What it bought is a real boundary with tests on both sides, one fewer diverged duplicate implementation, and a crash removed from the shipped app.

### Outcome

Playwright 91 → **93**. Vitest 67 → **70**.

## B5b — v120: Helper and vault view extraction (second slice)

### Goal

Finish the vault slice B5 stopped short of: move the HTML fragment builders into `src/vault/view.js`.

### The blocker, and what removing it exposed

B5 stopped because the builders needed `tagSpan`, `fmtShort` and `fileSizeStr`. Clearing that revealed a wider instance of the same defect the vault had: **`app.js` held byte-identical copies of five helpers that `src/lib/helpers.js` already exported** (`isoDate`, `todayISO`, `shiftDays`, `clamp`, `debounce`), plus sole copies of five pure formatters (`fmtShort`, `fmtFull`, `fmtWhen`, `fmtDur`, `timeAgo`). Two implementations, free to drift, with nothing pointing that out.

### Design

**Move C — pure helpers → `src/lib/helpers.js`.** The five duplicates deduplicated, the five formatters moved in, `app.js` reduced to one-line delegators (`app.js:101-114`). 7 new unit tests, including one that pins the non-obvious behavior in `fmtShort`: a bare `'YYYY-MM-DD'` parses as UTC and renders the previous day west of Greenwich, which is why the implementation appends `T00:00:00`.

**Move D — vault fragment builders → `src/vault/view.js`.** `vaultHost`, `vaultSort`, `vaultTagSet`, `vaultCardHTML`, `vaultRowHTML`. State reaches them through an injected deps object (`{ collections, tasks, tagSpan }`), the same pattern `src/lib/parser.js` established in v104 — not by importing app state.

`COVER_COLORS` moved to `src/lib/constants.js`. It is shared by the task cover picker and the vault card fallback, so it belongs in neither feature module. This restores `LumenLib.constants`, which **B4 removed four builds earlier for having zero consumers** — it now has one. The namespace inventory test moved 10 → 9 → 10 across the two builds; both edits were correct at the time.

### Why this one is worth more than its line count

The builders interpolate user-controlled data — item titles, collection titles, descriptions, tags — directly into HTML, and had **no unit test of any kind**. Extracting them made them testable, and the 12 tests added include escaping assertions for a hostile item title and a hostile collection title. That coverage did not exist in any form before, at any level.

### What stays in app.js

`renderVault` and `openVaultModal`. They bind DOM events and reach into a dozen app closures; "given an item, produce its markup" is a different ownership boundary from "wire up a view".

### Outcome

Vitest 70 → **89**. Playwright 93/93 unchanged, which is the point: no behavior moved.

## B5c — v121: Vault view rendering (third slice)

### Goal

Draw the boundary B5b named but did not cross: separate *producing the vault view's markup* from *wiring it up*.

### Design

`renderVault` was ~40 lines of markup followed by ~40 lines of event binding, in one function. The markup half became `vaultViewHTML(ctx)` in `src/vault/view.js`; `renderVault` now resolves state into a ctx, writes the result, and owns the bindings — which stay, because they reach into `bindFilterInput`, `setVaultViewMode`, `openVaultModal`, `addVaultCollection`, `toastQuota` and a recursive `renderVault`.

`vaultWidgetHTML` (the dashboard card) moved the same way, taking the item list as its one argument.

**Every line of markup was lifted programmatically, not retyped.** The extraction script reads the exact source lines out of `app.js` and applies identifier substitutions (`state.vaultItems` → `allItems`, `vaultFilter.` → `filter.`, `vaultQuotaUsed()` → `quotaUsed`, and so on). For markup this dense — nested template literals, emoji, conditional fragments — retyping is where behavior drift comes from.

### Outcome

Vitest 89 → **102**; 13 new tests covering grid-vs-list mode, the "N of M items" count, the two distinct empty states (nothing in the vault at all vs. filters matching nothing), selected-filter marking, type-count summarisation, the six-item cap with pinned-first ordering, and escaping of a hostile search query and item title.

Playwright 93/93 unchanged, which is the point: no behavior moved.

`app.js` 13,738 → 13,695. `src/vault/` is now 261 lines across two modules that are fully unit-tested; before v119 it was 68 lines of placeholder that the app shadowed at runtime.

## B5d — v122: Vault modal form (final slice)

### Goal

Finish the vault. `openVaultModal` was the piece v121 explicitly declined to attempt.

### Design

Same split as v121, applied to a bigger surface. `openVaultModal` was 151 lines: ~8 building option strings, ~33 of form markup, and ~110 of event binding. The first two became `vaultModalHTML(v, ctx)` in `src/vault/view.js`; the bindings stayed, because they own `pendingFile` as mutable closure state, drag-and-drop handlers, the IndexedDB blob write, and the save path.

`vaultLinkPickerHTML` moved with it — four lines, but it renders vault items into *other* features' modals, so it belongs with the rest of the vault's presentation.

Markup was again lifted programmatically rather than retyped: the script reads the source lines and substitutes `state.tasks` → `tasks`, `getStudentsList()` → `students`, `allCols` → `collections`.

### What the tests caught that nothing else could

The picker caps — 80 tasks, 30 goals, 30 notes, 50 students — existed in the original code with no test and no comment. They are now asserted, so a future edit that drops a `.slice()` fails a test instead of quietly rendering thousands of checkboxes in a modal.

The 11 new tests also pin: edit-vs-new titling, Delete appearing only when editing, pre-selected type and collection, checked state for already-linked items, the pending-file description, Remove appearing only for a stored blob, escaping of a hostile title in an attribute context, and that the form closes through `data-close-modal` rather than an inline `onclick` — which pins the v115 contract at the point it is easiest to regress.

### End state of the vault

| Layer | Owner |
| :-- | :-- |
| IndexedDB blobs, quota sum, type classification | `src/vault/store.js` |
| All markup — cards, rows, widget, view, modal form, link picker | `src/vault/view.js` |
| State reads, filters, view mode, event binding, blob writes | `app.js` |

Every vault presentation function left in `app.js` is a one-line delegator. `src/vault/` is 326 lines with 36 unit tests; before v119 it was 68 lines of placeholder that the running app shadowed, with one test.

Vitest 102 → **113**. Playwright 93/93 unchanged. `app.js` 13,695 → 13,657.

## B6 — v123: README truth-up, focus contrast, app-shell accessibility

### README

Audited every claim against the code rather than fixing only the two known-wrong badges.

- `Zero-Build` / `No Build Step` → `No Framework`. Vite has bundled the app since v116; there is genuinely no framework.
- "no bundlers, no frameworks, no external dependencies" → rewritten. PeerJS is vendored, and Vite bundles for production.
- "military-grade client-side encryption" → the actual spec (AES-256-GCM, PBKDF2-SHA-256), which is both true and more informative.
- Persistence listed one IndexedDB store; there are four (`lumen-state`, `lumen-audio`, `lumen-vault`, `lumen-vault-auto`).
- The shortcut table was missing <kbd>H</kbd>, <kbd>Space</kbd> and <kbd>Ctrl+Shift+D</kbd>, all of which the key handler implements.

**The substantive finding was in the privacy section.** `startPeer` calls `new PeerCtor(syncMeta.peerId)` with no options, so peer sync runs on PeerJS's bundled defaults: the public broker at `0.peerjs.com`, a Google STUN server, and PeerJS TURN relays as fallback. The README's "Zero Third-Party Database" framing invited the reading that nothing third-party was involved. It now names all three, and states that WebRTC's DTLS means a relay carries ciphertext while the broker and STUN see peer IDs, IPs and connection metadata.

### Focus-indicator contrast — measured, not guessed

B3 (v117) claimed six `outline: none` rules made focus invisible; that was wrong, and the correction stood as "unproven, needs measurement". It has now been measured across all **15** palettes (14 themes plus `:root` — the earlier "eleven" was also wrong).

| Indicator | Result |
| :-- | :-- |
| The `rgba(96,93,255,.18)` ring | **1.14–1.27:1 in every palette.** Hardcoded, so it never followed the theme either |
| Border colour change (`--border` → `--accent`) | carries 9 palettes; **fails in sepia, sunset, cerulean, coral-dawn, campus and calm** |
| A solid `--accent` outline | still fails campus (2.77:1) |
| `--text-strong` | **passes everywhere**, worst case nord 5.03:1 |

So 6 of 15 themes shipped with no WCAG-conforming focus indicator. Fixed with `html :focus-visible { outline: 2px solid var(--text-strong) }` — the `html` prefix is load-bearing, since a bare `:focus-visible` loses the specificity tie to the `outline: none` rules.

`tests/unit/focus-contrast.test.js` parses the real rule out of `styles.css`, resolves its token in every palette and asserts 3:1 — so it fails if the rule is removed, weakened, or if a new theme arrives with a palette that cannot carry it. A companion Playwright test proves the rule actually reaches a date input, and was verified to fail with the CSS removed.

### App-shell accessibility

B3 covered dialogs; everything outside one was untouched. Surveyed, then fixed:

- `<nav>` had no accessible name → `aria-label="Main"`.
- **Zero `aria-current` anywhere.** The active view was a CSS class only. Now `aria-current="page"` marks the real destination — a view reached through "More" marks its More entry, not the button that opens the menu.
- `#toast-root` was an inert div, so **every toast was silent to a screen reader**. Now `role="status" aria-live="polite"`, declared in `index.html` so the region exists before content lands in it.
- `#view-root` is now named by the topbar `<h1>`, so the content region announces as "Notes", "Tasks" and so on.
- `<aside class="sidebar">` → `<div>`. `<aside>` means `role="complementary"` — "tangentially related" — which is the opposite of the truth for the app's primary navigation.

That last change touched a CSS rule and a JS lookup that both keyed off the `aside` tag, and **nothing covered focus mode**, so it could have broken silently. Verified manually, then pinned with a regression test.

### Outcome

Playwright 94 → **100**. Vitest 113 → **115**.

## B7 — v124: Task card extraction

### Goal

Apply the vault pattern to a second view, starting with the most-rendered markup in the app.

### Design

`taskCardHTML` turned out to be 53 lines, not the ~260 a first read suggested — the rest belonged to the Eisenhower matrix function below it. ## B11 — v128: Schedule week grid, and a real timezone bug

### Goal

Finish `renderSchedule`: the week/timetable branch left over from B10.

### The bug

`buildWeekDays` computes each day of the week at **local** midnight, then the original code serialized it with `dt.toISOString().split('T')[0]`. `toISOString()` converts to UTC first — so in any timezone ahead of UTC, local midnight is still the previous day in UTC, and the date string comes out one day early.

The effect is intermittent, which is exactly why it survived: the bug only fires while the local clock is still inside the UTC offset window. For UTC+3 (e.g. Istanbul), that is roughly 00:00–03:00 local. Outside that window the date arithmetic happens to land past the UTC boundary and the bug is invisible. A first attempt at an E2E regression test ran at 14:35 local and passed — the bug wasn't reproducible at that hour. It was rewritten using Playwright's `page.clock.install()` to pin the moment to 01:00 local alongside a fixed `timezoneId`, which reproduced it exactly: **"today" landed on the 30th instead of the 29th.**

Fixed by formatting from local `getFullYear`/`getMonth`/`getDate` instead — the same trick `src/lib/helpers.js#fmtShort` already uses on the parsing side of this exact trap.

### Extraction

Three pieces moved into the existing schedule modules, completing the pattern from B10:

- **`buildWeekDays(monday, days, todayISOStr)`** → `src/lib/schedule.js`. Matches "today" by date, not by weekday id, so a stale flag can never point at the wrong week.
- **`buildScheduleGrid(tasks, periods, days)`** → same module. Files tasks into a period × day grid and reuses `timeOverlaps` to flag clashing cells; a task addressed to a period or day that no longer exists is dropped rather than thrown, since periods and days are user-configurable.
- **`weekGridHTML(ctx)`** → `src/schedule/view.js`. The day-header row, one row per period, one cell per day. Cell markup comes in via `cellHTML`, because only the caller knows the overlap set and today's date.

`timeOverlaps`'s delegator in `app.js` became dead once `buildScheduleGrid` called the module's own copy directly, and was removed.

### Outcome

Vitest 184 → **201**; 17 new tests, including one invariant (`buildWeekDays` marks exactly the day matching today's date, never zero and never more than one) and a month-boundary case (a week starting Aug 31 rolls correctly into September). Playwright 101 → **102**, the new one being the timezone regression itself.

`app.js` 13,309 → **13,252**. `renderSchedule` 369 → 313 lines — what remains is the outer shell (view-mode toolbar, navigation, the unscheduled/committed trays) and the drag-and-drop wiring, which reach into a dozen app closures the same way `openVaultModal`'s binding does.

## B15 — v132: Student revenue-format dedup, and app-wide form accessibility

### Student revenue formatting

### Form labelling — systemic, app-wide

**Zero of the app's 105 `<label>` elements used `for`.** Every form field in every modal is associated with its label only by visual proximity — a screen reader announces the input with no name at all.

The fix had two parts, because the labels split into two genuinely different kinds:

- **92 field labels** — a label immediately followed by the single input/select/textarea it names. Given `for="<that id>"`.
- **13 group labels** — a label naming a *set* of controls: a colour-swatch picker, a checkbox grid of linked items, a repeatable subtask/comment list, a card-actions button row. `for` has no target to point at for these; each got `role="group"` on its container plus `aria-labelledby` pointing back at the label.

**A mistake worth recording.** The first attempt at the mechanical fix used one `String.replace()` with a non-greedy `[\s\S]*?` spanning the whole 13,000-line file. It reported 59 fixes instead of the expected 69, silently — the failure mode wasn't an error, it was a regex that backtracked past a label it couldn't immediately match, swallowed forward through several *other*, perfectly matchable labels looking for the next available input tag, and produced one wide incorrect match that skipped all of them. The fix was reverted from a clean backup and rewritten to inspect each label individually with a small bounded window, which cannot cross into unrelated content. Every one of the 105 additions was then verified programmatically — every `for=` value resolves to a real `id`, no duplicates — before any browser test ran.

The sweep also had to reach past `app.js`: three of the six modals it started with (task, vault) had their markup already living in `src/tasks/view.js` and `src/vault/view.js` from earlier builds, and the first pass missed them entirely.

7 new browser tests drive real modals (goal, task, vault, settings) and assert every visible label resolves.

### Table headers

None of the app's 44 `<th>` cells declared `scope`. All are genuine column headers (no row headers found), so this was a safe, mechanical `scope="col"` add-everywhere — verified with a browser test across finance, students and analytics.

### Heading order — audited, not fixed

A single `<h1>` (the topbar view title) is followed almost everywhere by `<h3>` — 94 occurrences, skipping `<h2>` nearly entirely, with 8 `<h4>`s nested under some of them. This is a real, systemic gap. It was **not** fixed here: those 94 `<h3>` elements serve at least two semantically different roles — a modal's own title (`.modal-head h3`, arguably fine to leave since a `role="dialog"` gets its own accessible navigation context) and a main-view section heading (`.card-title`, which sits directly under the page's `<h1>` with nothing between and probably should be `<h2>`). Reclassifying 94 call sites by which role each one plays is a judgment call, not a mechanical fix, and doing it under time pressure risked getting the split wrong. Recorded precisely so it can be done properly.

## B21 — v138: Heading-order reclassification

### Goal

Fix the page's heading hierarchy: every view had exactly one `<h1>` (the shared `#view-title` bar in `index.html`) followed directly by a wall of `<h3>` section headings, skipping `h2` entirely. 91 `<h3>` elements needed per-site classification, not a mechanical find-and-replace — the B15 lesson (a single unbounded regex silently mismatched at this file's scale) applied directly here too.

### Design

Classified all 91 sites by what they actually are, not by assumption:

- **69 main-view section headings** — every `h3.card-title` (68 of them, across dashboard, tasks, schedule, finance, students, notes, habits, goals, projects, achievements, focus, analytics, activity, perf and settings) plus the students-roster empty state (`Your Student Roster is Clean & Ready`, a bare `<h3>` with the same role but no `card-title` class). All 69 sit directly under the page's single `h1` with nothing between — promoted to `<h2>`.
- **22 modal-dialog titles** — every `<h3>` inside a `.modal-head` (13 with the class literally on the same line, 9 confirmed by tracing each one back to its enclosing `openModal(` call: Focus Hub, project editor, attendance/assignment/lesson-plan editors, the student dossier, "Add/Edit Student Profile"). Left as `<h3>` — a dialog's accessible name comes from `role="dialog"` + `aria-labelledby` (wired in v123), not from its position in the page's heading order, and a closed (undisplayed) dialog isn't part of the accessibility tree an auditor like axe would walk anyway. The student dossier's own internal `<h4>` subsections (profile, financial metrics, linked goals, linked resources, learning goals, teacher notes) already nest correctly one level below its `<h3>` and needed no change.
- One pre-existing `<h2>` (the Keyboard Shortcuts modal) was left untouched — it predates this build and isn't part of the 91 `<h3>` sites being reclassified.

Verified the classification programmatically before editing: walked backward from every `h3.card-title` line looking for an enclosing `openModal(`` call, confirming zero of the 68 were modal content. Applied the promotion as 69 exact per-line string replacements (verified against the live line content, one `<h3`→`<h2` and one `</h3>`→`</h2>` per site, including the one site — the Deadlines widget — where the opening and closing tags are on different lines) rather than a single regex pass over the whole file.

Caught one real regression before it shipped: `styles.css`'s `.card h3.card-title` rule is tag-qualified, so it stopped matching the moment those elements became `<h2>` — font-size, weight and the flex layout would have silently dropped. Fixed by dropping the tag qualifier to `.card .card-title`, which is also more correct going forward regardless of which element carries the class. Confirmed in a live preview: the Dashboard now reports exactly one `h1`, all card-titles as styled `h2`s, and zero `h3`s outside an open modal; opening the "New habit" modal shows its title still rendering at the `.modal-head h3` size and weight.

### Outcome

Vitest 340 unchanged (no unit-level coverage of app.js's own markup strings). Playwright 109/110 unchanged. `app.js` line count essentially unchanged (a tag-name swap, not a structural edit) at 12,669.

This closes the accessibility audit opened in v123: modal semantics, non-modal landmarks/aria-current/toast live region, form labelling, table header scope and heading order are now all addressed.

## B22 — v139: The last skip, a real label bug behind it

### Goal

`tests/a11y-forms.spec.js` carried two conditional `test.skip`s written when their target UI wasn't reachable yet from a test. One (`student edit modal`) had already been fixed by an earlier build without anyone circling back to remove the now-stale skip guard; the other (`personal schedule interval modal`) was still skipping every run because its selector guessed at a trigger (`[data-open-personal-schedule], #sched-settings, [id*="personal-schedule"]`) that never matched the app's real one.

### Design

Traced the real trigger: `openScheduleIntervalsModal` is bound to `#sched-intervals`, the "⚙️ Intervals" button in the schedule toolbar — not any of the selectors the test guessed at. Swapped in `page.click('#sched-intervals')` and dropped `openStudentEditModal`'s now-unnecessary `?.()` optional-chaining guard and its `test.skip`, since the function has been on the `__LUMEN_TEST` seam since it was added.

Running the un-skipped personal-schedule test for the first time immediately failed with 37 unassociated labels — a real, previously-invisible bug the skip had been hiding rather than a test-authoring mistake. The "Advanced — edit current intervals individually" section renders one row per period with Label/Start/End inputs addressed only by `data-edit-*` attributes, no `id`; their sibling `<label>`s carried no `for`. A screen reader announced every one of those inputs with no name. Fixed by giving each input an id keyed on its period's own id (`ps-adv-label-${p.id}`, etc. — already unique, already used for `data-period-id`) and pointing each label's `for` at it, in both the initial render and the "+ Add interval" handler that inserts new rows at runtime. A third label ("Preview") turned out to be mislabeling a static, non-interactive preview `<div>` — not a form control at all — so it was changed from `<label>` to a plain `<div class="field-label">`, which is what the other read-only section headers in this same modal already use.

Verified live in the browser rather than trusting the test alone: clicked `#sched-intervals`, checked every label's `for` resolves to a real element for all 12 default periods, then clicked "+ Add interval" and confirmed the freshly-inserted row's labels resolve too.

### Outcome

Vitest 340 unchanged. Playwright **109/110 (1 skip) → 110/110 (0 skips)** — the last skip in the suite is gone, and it uncovered a real defect rather than just closing a gap in coverage.

This closes the accessibility line of work for good: every skip in the test suite either passes now or has been deleted because what it guarded no longer applies.
