## Shared context

### What Lumen is

A local-first personal productivity PWA for a solo knowledge worker who is also a teaching professional. Pure vanilla HTML/CSS/ES2022, no bundler, no framework, no mandatory backend. State in `localStorage` (`lumen.state.v1`) + IndexedDB (`lumen-state` for state snapshots, plus voice blobs and a 3-slot rotating encrypted auto-vault). Optional P2P sync (PeerJS/WebRTC, lazy-loaded). Optional AI via a bring-your-own Google Gemini key.

The product thesis is **interconnection**: completing a task bumps a linked KR; a habit protects a goal deadline; a note checklist becomes tasks; a focus session logs to analytics and streaks. Every build must make a link *more visible or more load-bearing* — never add an isolated feature.

### Constraints carried across all three builds

- **Local-first.** No new mandatory cloud dependency. P2P stays PeerJS, lazy-loaded.
- **Offline shell stays green.** `tests/offline.spec.js` boots the app with the dev server killed. Any new file that `index.html` loads at boot MUST be added to the `sw.js` `SHELL` precache array (`sw.js:6`).
- **Zero-build for the app.** `app.js` stays a classic `<script>` (not `type=module`) — it relies on hundreds of inline `onclick="fn()"` handlers that need functions in global scope. Only *new* `src/lib/` code may be ES modules, loaded through a single bootstrap module (see Build A).
- **Release ritual.** Every build bumps `sw.js` `VERSION` (`lumen-cache-v10x`), the `?v=10x` asset query in `index.html` (3 occurrences: `styles.css`, `themes.css` prefetch, `app.js`), and tags `v10x`. The SW `activate` handler already deletes non-current caches (`sw.js:48`).
- **State back-compat.** `normalizeState(parsed)` (`app.js:756`) is the single migration funnel. New fields are additive with sane defaults. Never rename or drop an existing field without a migration in `normalizeState`.
- **Vault format back-compat.** The encrypted backup envelope is `{ lumenEncrypted:true, version:1, salt, iv, data, exportedAt }` (`app.js:456`). Files exported by any prior version must still decrypt.
- **Existing tests are the safety net.** All 43 Playwright specs stay green with assertions unchanged. New behavior gets new specs.

### Test infrastructure today

- Playwright only. `playwright.config.js` serves the static dir on `:8092`, `tests/*.spec.js`, chromium, `retries: 0`.
- Specs seed and clean state through `page.evaluate(() => { /* touch global `state`, call `save()` */ })`. `state`, `save`, and most top-level functions are browser globals.
- CI: `.github/workflows/ci.yml` runs `npm ci` → `playwright install chromium` → `npm test` on push/PR to `main`.
- **No unit layer.** Pure logic (natural-language parser, vault crypto, sync merge, schedule generation) is only exercised through full-browser E2E.

## Build A — v104: Trust Layer + Test Seam

### Goal

Stand up a Vitest unit-test seam by extracting Lumen's pure logic into `src/lib/` ES modules, and harden the two "trust" surfaces the README advertises but under-delivers: the sync passphrase hash and the Gemini API call.

### Non-goals

- No full Vite migration, no `app.js` split beyond the four pure-logic modules below.
- No TypeScript. New modules are plain `.js` with JSDoc `@param`/`@returns` annotations.
- No Web Worker for PBKDF2 (deferred to Build C, which owns the perf pillar).
- No UX change. Every existing screen behaves byte-identically.

### Design

**Module seam.** Four new ES modules under `src/lib/`, each a set of pure functions that take every input as a parameter:

| Module | Exports | Extracted from |
| :-- | :-- | :-- |
| `src/lib/crypto.js` | `buf2b64`, `b642buf`, `deriveVaultKey`, `encryptVaultBackup`, `decryptVaultBackup`, `hashPassLegacy`, `hashPass`, `randomSaltB64` | `app.js:421-484`, `app.js:7592-7596` |
| `src/lib/schedule.js` | `timeToMin`, `minToTime`, `generatePeriods` | `app.js:1131-1151` |
| `src/lib/parser.js` | `parseNaturalLanguageTask(rawText, deps)` | `app.js:487-621` |
| `src/lib/merge.js` | `applyMerge(ctx)` | `app.js:7748-7895` |

**Browser bootstrap.** `src/lib/globals.js` is an ES module that imports the four and assigns `window.LumenLib = { crypto, schedule, parser, merge }`. `index.html` loads it with `<script type="module" src="src/lib/globals.js?v=104"></script>` placed **immediately before** the `app.js` script tag. Per the HTML spec, a module script and a `defer` classic script execute in document order after parsing completes, so `globals.js` runs first and `window.LumenLib` is populated before `app.js` executes.

**Delegators.** In `app.js`, the extracted functions keep their `function` declarations (preserving hoisting) but their bodies become one-line delegators, e.g.:

```js
function encryptVaultBackup(plainText, password) {
  return window.LumenLib.crypto.encryptVaultBackup(plainText, password);
}
function parseNaturalLanguageTask(rawText) {
  return window.LumenLib.parser.parseNaturalLanguageTask(rawText, {
    students: getStudentsList(),
    projects: state.projects || [],
    goals: state.goals || [],
    now: new Date(),
  });
}
```

Call sites in `app.js` are unchanged (~40 for the parser, ~10 for crypto, 1 for merge).

**`applyMerge` separation of concerns.** The extracted `applyMerge(ctx)` takes `{ state, syncMeta, inc, incomingRev }`, mutates `state` and `syncMeta` in place (same object references), computes and returns `changed: boolean`, and — when changed — bumps `syncMeta.rev`. It does **not** call `save()`, `saveSyncMeta()`, or any render function. The `app.js` delegator keeps those side effects:

```js
function applyMerge(inc, incomingRev) {
  const changed = window.LumenLib.merge.applyMerge({ state, syncMeta, inc, incomingRev: incomingRev || 0 });
  saveSyncMeta();
  if (changed) { save(); if (currentView() === 'settings') renderSettings(); else renderView(); }
  return changed;
}
```

**Sync passphrase hardening.** Today `hashPass(p)` is a single unsalted `SHA-256('lumen-sync::' + p)` (`app.js:7592`). The P2P channel is not end-to-end encrypted, so this hash is a "same passphrase" handshake gate, not data protection — but it is still trivially brute-forced against a weak passphrase and identical across devices. Build A:
- Adds `hashPass(passphrase, saltB64)` — PBKDF2, 100k iterations, SHA-256, hex output — and keeps `hashPassLegacy(p)` for verifying pre-v104 peers.
- `syncMeta` gains `passSalt: string` and `passHashV: 1 | 2`.
- Setting a passphrase (`app.js:12225`) generates `passSalt` once and stores `passHash = hashPass(v, passSalt)`, `passHashV = 2`.
- The `hello` handshake (`app.js:7703-7718`) sends `{ pass, passV, salt }`. Match logic: both v2 → compare v2 hashes; both v1 → compare v1; version mismatch → toast `"One device needs its sync passphrase re-entered (Settings → Sync) to upgrade security"` and close, exactly as today's mismatch path does.
- On first load after v104, if `syncMeta.passHash && !syncMeta.passSalt`, show a one-time dismissible toast nudging the user to re-enter the passphrase. Legacy v1 verification keeps working until they do.

**Gemini hardening.** `callGemini(prompt, systemInstruction)` (`app.js:626`) gains:
- `AbortController` with a 12 s timeout; on abort throw `Error('GEMINI_TIMEOUT')`.
- One automatic retry on HTTP 429 or 5xx, after a 1.5 s wait.
- `NO_API_KEY` is caught by callers and surfaced as an inline link to Settings, not a toast. (Add a helper `geminiKeyMissingCTA()` returning an HTML string; callers already `try/catch`.)
- The Morning Brief AI daily focus (`app.js:2286`) caches its result in `state.settings.aiDailyFocus` + `state.settings.aiDailyFocusAt` keyed by `todayISO()`; a same-day re-render reuses the cache instead of re-calling.

### Testing

- **Unit (Vitest, `environment: 'node'`, Node 20 global WebCrypto):**
  - crypto: encrypt→decrypt round-trip; wrong password → `"Incorrect vault password or damaged data."`; non-envelope → `"Not a valid Lumen encrypted vault file."`; `hashPass` deterministic given salt, differs from `hashPassLegacy`, salt-sensitive.
  - schedule: `generatePeriods` returns `null` for `end <= start`, `interval < 5`, `interval > 240`; skips a break window; exact-fit boundary (`08:00`–`09:00` @ 60 → 1 block); ids sequential `p1..pN`.
  - parser: priority tokens (`!high`→`high`), tags (`#foo`), `tomorrow`/`today`/`in 3 days`/`next monday`/ISO date, `at 3pm`→`15:00`, `@Name` matching an injected student, title cleanup, `null` for empty.
  - merge: incoming newer `updatedAt` wins; tombstoned id stays deleted; `tagColors` per-key delete via meta timestamp; `changed` false when nothing new; `incomeTypes` union + tombstone removal.
  - gemini: `fetch` mocked — success returns text; 429 then 200 retries once; two 429s throws; abort path throws `GEMINI_TIMEOUT`.
- **E2E (Playwright):**
  - `tests/regression.spec.js`: new case asserting `window.LumenLib.crypto` and `window.LumenLib.parser` exist and the app boots with zero console errors.
  - `tests/perf.spec.js` (new): seed 2,000 tasks via `page.evaluate`, navigate to `#dashboard`, assert the last `window.Lumen.perfLog` entry for `dashboard` is `< 50` ms and matrix initial render `< 16` ms.
  - Passphrase: set in Settings → Sync, reload, assert `syncMeta.passSalt` is a non-empty string and `syncMeta.passHash` is 64 hex chars.
  - All 43 existing specs stay green.

### Risks

| Risk | Mitigation |
| :-- | :-- |
| Module/`defer` execution order differs in some browser | Document-order execution is spec-guaranteed for module + defer classic scripts. The new regression spec asserts `window.LumenLib` exists at boot; `offline.spec.js` covers the cached path. |
| `applyMerge` references an `app.js` global not passed in `ctx` | Task extracts it behind **characterization tests first** (snapshot current behavior), then moves code, then re-runs. A `grep` step lists every identifier the function uses. |
| `parser` behavior drift from the injected-deps refactor | Golden-fixture unit tests written against current output *before* the extraction; extraction must keep them green. |
| SW caches stale `src/lib/*.js` between releases | `import` specifiers in `globals.js` stay bare; the `VERSION` bump re-`add`s the whole `SHELL` on `install` and `activate` purges old caches — same contract as every other asset. |
| Node WebCrypto vs browser SubtleCrypto divergence | Both implement the W3C Web Crypto API; the extracted crypto uses only `crypto.subtle` + `crypto.getRandomValues`. The Playwright crypto spec (`behavioral.spec.js:169`) still runs in a real browser. |

## Build B — v105: Teaching Wedge Weave

### Goal

Make the teaching wedge load-bearing: student identity becomes a real foreign key, goals link to students explicitly, and finance rolls up per student — so the "Teaching Command Hub" reflects wired data instead of a string-matching heuristic.

### Non-goals

- No new top-level nav item. Reuse `students`, `finance`, `goals`, `schedule` views.
- No multi-user or per-student login.
- No accounting features beyond Paid / Expected / Outstanding rollups.

### Design

**The problem.** `income` entries key the student by **display name string** (`app.js:9101`: `student: student || undefined`; `app.js:9876`: `student: studentName`). `teachingDashboardHTML` (`app.js:2697`) then links goals to students with a brittle word-overlap heuristic (`app.js:2706`: `w.length > 3 && gt.includes(w)`) and matches income with `e.student === s.name || e.student === s.id` (`app.js:2708`). Rename a student and their income orphans; two students named "Ana" collide.

**FK canonicalization.** In `normalizeState` (`app.js:756`), after `getStudentsList()` has run its own legacy migration (`app.js:822`):
- Build a `name → id` map from `state.students`.
- For each entry in `state.income`, `state.expectedIncome`, `state.assignments`, `state.attendance`: if it has a `student` name (or `studentName`) but no `studentId`, set `studentId` from the map. Keep the original `student` string as a display fallback. If no match, leave `studentId` unset and `logActivity('finance.orphan', ...)` once.
- New income/attendance/assignment writes set **both** `studentId` (canonical) and `student` (display).

**Goal → student link.** `goal.linkedStudentIds: string[]` (additive, default `[]`). The goal modal (`app.js:5738`) gains a "Linked students" multi-select built from `getStudentsList()`, persisted in the `data` object at `app.js:5786`. Goal cards render student chips. `teachingDashboardHTML` uses `goal.linkedStudentIds.includes(s.id)` first and falls back to the existing heuristic only when `linkedStudentIds` is empty.

**Per-student finance rollup.** A new card in `renderFinance` (`app.js:8563`): for each active student, `Paid` (sum of `income` where `studentId === s.id`), `Expected` (sum of `expectedIncome`), `Outstanding` (`Expected − Paid`, floored at 0), grouped by `currency` (`USD` / `TRY` shown separately). Rendered with `fmtM(v, curr)` (`app.js:8558`) and `div`-width bars — no chart library.

**Dossier deepen.** The student dossier (`openStudentDossier`) gains:
- A "Linked goals" strip: chips for every goal where `linkedStudentIds.includes(s.id)`, each showing `goalProgress(g)%`.
- The finance tab shows the last 5 `income` rows for `studentId === s.id` and a "Log income" button that opens the finance entry modal prefilled with `studentId`, `currency: s.currency`, and `rate: s.rate`.

**Lesson-plan → task bridge.** The existing "Create tasks" action in the Lesson Planning Workstation (`app.js:10086`) propagates `studentId` onto the created tasks so `teachingDashboardHTML`'s planned-lesson and active-task counts reconcile.

### Testing

- **E2E (`tests/wedge.spec.js`):**
  1. Seed via `page.evaluate`: student `{ id:'s-caner', name:'Caner Yilmaz', currency:'TRY', rate:1500 }`; legacy income `{ student:'Caner Yilmaz', amount:1500, currency:'TRY', date: today }` with **no** `studentId`.
  2. Reload → assert that income entry now has `studentId === 's-caner'` (FK backfill ran).
  3. Create goal "IELTS 8.0", open its modal, select Caner in Linked students, save → assert `state.goals[0].linkedStudentIds` contains `s-caner`.
  4. Navigate `#finance` → assert the per-student card shows Caner with `₺1,500` paid.
  5. Navigate `#dashboard` → assert the Teaching Hub row for Caner shows the IELTS goal chip (from the explicit link, not the heuristic).
  6. Open Caner's dossier → assert the linked-goal chip renders with a progress %.
- **Migration safety:** seed an income entry whose `student` name matches no student → reload → assert `studentId` stays unset and the app renders without error.
- All 43 existing specs + Build A's specs stay green. `behavioral.spec.js:447` (TRY currency + student name) must still pass unchanged.

### Risks

| Risk | Mitigation |
| :-- | :-- |
| FK backfill orphans income on a name typo | Keep the `student` display string; never delete it. Unmatched entries keep working by name; `logActivity` records the orphan. |
| Two students, same name | The `name → id` map keeps the **first** match and `logActivity('finance.orphan.ambiguous', ...)`. Dossier "Log income" always writes `studentId`, so new data is unambiguous. |
| `_teachingMemo` serves stale weave after a goal link edit | `_teachingMemo` is keyed on `_stateRev` (`app.js:2698`); a goal edit already bumps `_stateRev`. Add `goal` to the invalidation trigger list if not present. |
| Multi-select in the goal modal bloats a small modal | Render as a compact chip-toggle row, not a `<select multiple>`; only shown when `getStudentsList().length > 0`. |

## Build C — v106: Review Ritual + Mobile Reach

### Goal

Turn the Weekly Review from a backward-looking report into a guided reflect-and-commit ritual, and make the four heaviest views usable one-handed on a phone. Fold in the PBKDF2 Web Worker deferred from Build A.

### Non-goals

- No Electron/Capacitor. PWA install path only.
- No redesign of the Review view's data model — it keeps `reviewCtx(off)` (`app.js:3463`) and the Markdown export (`app.js:3622`).
- No new nav item.

### Design

**Review today.** `renderReview` (`app.js:3610`) already shows stat cards, hidden-overdue, deadline health, completed-this-week, goal progress, achievements, and habit week — all *retrospective*. `reviewSkeletonHTML` (`app.js:3562`) lays them out. There is no forward-looking step and no sense of "ritual".

**The ritual.** Add a fourth panel group above the retrospective cards — a three-step strip, each step one click to advance:
1. **Shipped** — completed tasks + habit check-ins + KR gains in the window (data already in `reviewCtx`). One-line summary + a celebratory count.
2. **Slipped** — hidden-overdue tasks (`ctx.hiddenOverdue`), habits with ≥2 misses in the last 7 days (reuse the `decayHabits` computation from `app.js:8372`), and KRs whose progress did not move. Each row links to the relevant view.
3. **Protect next week** — pick up to 3 items to carry forward: decaying habits, goals with a deadline inside 14 days, and any "Slipped" task. Selected items are written to `state.settings.reviewCommit = { weekStart, taskIds:[], habitIds:[], goalIds:[], at }`. The Morning Brief's "Today's candidates" bucket (`app.js` Brief commit) reads `reviewCommit` and surfaces those items first for the coming week.

The Markdown export gains a "Protecting next week" section from `reviewCommit`.

**Ritual is opt-in-visible, never blocking.** The strip renders collapsed with a "Start weekly review" button when `reviewCommit.weekStart !== currentWeekStart`; expanded and checkmarked once done. No overlay, no gate — consistent with the Brief's soft-nudge pattern.

**Mobile reach.** Current breakpoints are scattered (`@media` at 600/640/768/860/900px in `styles.css`). The four heaviest views:
- **Kanban** (`styles.css:2839`) — already `scroll-snap-type: x mandatory` and `.col { min-width:260px }` under 860px. Add a sticky column header and a scroll-position dot indicator under 640px.
- **Finance** / **Students** / **Lesson Planning** — wide grids and tables. Under 860px: single-column card reflow, `overflow-x:auto` wrappers on any residual table, sticky view toolbar + full-width search.
- Global: `.topbar` sticky and `.topbar-right` wraps under 860px; tap targets ≥ 40 px.

**PBKDF2 Web Worker.** `src/lib/vault-worker.js` — a classic worker script that runs PBKDF2 + AES-GCM off the main thread. `src/lib/crypto.js` gains `encryptVaultBackup`/`decryptVaultBackup` variants that accept an optional `workerFactory` (`() => new Worker('src/lib/vault-worker.js')`); when `Worker` is undefined or the factory throws, they fall back to the current inline path. The public function signatures used by `app.js` do not change.

- **E2E (`tests/review-ritual.spec.js`):** seed completed tasks + a decaying habit in the current window → `#review` → assert the ritual strip renders "Shipped"/"Slipped"/"Protect"; click through, select a habit to protect, finish → assert `state.settings.reviewCommit.habitIds` contains it; navigate `#brief` → assert that habit appears in Today's candidates; export Markdown → assert the file contains "Protecting next week".

- All prior specs green. `behavioral.spec.js:169` (crypto round-trip in-browser) still passes with the worker path active.

### Risks

| Risk | Mitigation |
| :-- | :-- |
| Ritual reads as nagging | Collapsed by default, one button to start, never an overlay. Mirrors the accepted Brief soft-nudge. |
| `reviewCommit` and the Brief's own commit key (`lumen.brief.commitDate`) fight | `reviewCommit` only *orders* the candidates list; the Brief's own "Commit Day" remains the authority for what enters `today`. |
| Worker script fails under `file://` or strict CSP | Same-origin worker URL; `try/catch` around `new Worker` falls back to the inline path; unit test covers the fallback. |
| Mobile CSS regressions on desktop | `tests/mobile.spec.js` runs at 375px; the existing smoke suite runs at the default desktop viewport — both in CI. |
| Worker not in `sw.js` SHELL → offline crypto breaks | Task adds `./src/lib/vault-worker.js` to `SHELL` and the offline spec exercises a reload; add an assertion that encryption still works offline. |
